# v0 results: Timelake vs. naive Iceberg (S3 Tables pattern) vs. Lance

_2026-10-12, M1 Pro (10 cores), RustFS 1.0.1 behind tools/s3proxy (20 ms time-to-first-byte per request) for "s3". Method: [v0/README.md](../v0/README.md). Every query returned identical row counts on every engine._

## Summary

**Ingest:** 1,728 Firehose-style commits (5-minute windows), 23.3M rows.
| | Timelake | Lance | Iceberg (PyIceberg) |
|---|---:|---:|---:|
| S3 wall time | **434 s** | 817 s | 1,607 s |
| S3 commit p50 | **163 ms** | 425 ms | 922 ms |
| Local wall time | 25 s | **6 s** | 306 s |
| Objects after ingest | **1,082** | 5,187 | 6,921 |
| Live table size after maintenance | **228 MB** | 449 MB | 262 MB |

Timelake's numbers include its inline maintenance: 235 compactions plus snapshot expiry during the stream. The other two systems leave 1,729 small files that need a separate job. Lance's local appends are the fastest writes, but each one is a new fragment.

Timelake is also fastest on repeat runs in every state. The details below have per-query numbers.

**Plain DuckDB on Timelake tables** (no Timelake software) beats DuckDB on naive Iceberg on S3 by 7.8× (ingested) and comes within about 25% of it after maintenance. It trails DuckDB on the binpacked Iceberg tables (0.52 vs 0.42 s), whose PyArrow files need fewer requests. Timelake's own reader is the fast path.

### Where the wins come from
1. **Layout:** sorted by `(tags_id, time)` and partitioned by day, with inline size-tiered compaction. Right after the stream, Timelake tables have 24–45 live files and 6 manifests per table. Naive appends leave 864 files and 864 manifests.
2. **Last-value index:** `last-loc`, `low-fuel`, `high-load` and `one-truck-latest` read a small index instead of scanning. On S3 that is 12 requests for `last-loc` vs 1,733 (Iceberg) and 3,614 (Lance).
3. **Object-store-aware reading:**
   - all of a query's tables are loaded concurrently before planning,
   - each Parquet footer is read once,
   - scans use more partitions on remote stores,
   - files use 1M-row row groups with page indexes.

   This took S3-maintained TSBS from 0.465 s to about 0.25–0.29 s.
4. **Manifest merging:** an append keeps at most about 8 manifests, so planning stays a few reads. Naive PyIceberg appends leave 1,728 manifests, and DuckDB reads them all.

### Caveats
- **S3 Tables' managed compaction isn't reproduced.** The real service also expires snapshots and can sort if a sort order is configured. "Maintained" Iceberg here is binpacked and unsorted (the service default), with all snapshots kept.
- **Lance compaction on RustFS** failed with concurrent multipart uploads (`LANCE_UPLOAD_CONCURRENCY` > 1), directly and through the proxy. It ran with concurrency 1, directly against RustFS, so Lance's S3 maintenance time (13.5 s) has no added latency and is not comparable.
- **Timelake keeps replaced files for 1 h** (snapshot retention). "Total MB after" maintenance is therefore 522 MB while the live table is 228 MB.
- **Timelake's reader reuses a table version it loaded within the last 1 s** for planning. Its own commits are always visible.
- **This is one machine, one dataset, and a latency proxy instead of real S3.** Real S3 adds bandwidth limits and latency variance.
