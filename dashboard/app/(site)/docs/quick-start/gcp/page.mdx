# Google Cloud

Gateways upload CSV or Parquet files to a landing bucket. Each upload triggers a Cloud Run function that appends the file to a Timelake table in a second bucket. Cloud Scheduler calls a second function for maintenance.

Timelake hasn't been tested on Cloud Storage yet ([Limitations](/docs/limitations)). It reaches Cloud Storage through the same storage library as S3, and commits use Cloud Storage's generation preconditions.

The commands use the `gcloud` CLI and the `timelake` command ([install](/docs/quick-start#1-install)). Set these once:

```bash
export PROJECT=$(gcloud config get-value project) REGION=us-central1
export LANDING=$PROJECT-timelake-landing LAKE=$PROJECT-timelake-lake
export SA=timelake-ingest@$PROJECT.iam.gserviceaccount.com
gcloud services enable cloudfunctions.googleapis.com run.googleapis.com eventarc.googleapis.com \
  cloudbuild.googleapis.com artifactregistry.googleapis.com pubsub.googleapis.com cloudscheduler.googleapis.com
```

## 1. Create the buckets and the table

```bash
gcloud storage buckets create gs://$LANDING gs://$LAKE --location=$REGION --uniform-bucket-level-access
gcloud auth application-default login          # credentials Timelake reads on your machine
export TIMELAKE_WAREHOUSE=gs://$LAKE/warehouse
timelake create iot.readings --schema "time:timestamptz,device_id:string,temp:double,humidity:int" \
  --time-column time --series-key device_id
```

Use two buckets so that the lake's own writes never trigger the function.

## 2. Create a service account

The function runs as this account. It may read the landing bucket, read and write the lake bucket, and receive events:

```bash
gcloud iam service-accounts create timelake-ingest
gcloud storage buckets add-iam-policy-binding gs://$LANDING --member=serviceAccount:$SA --role=roles/storage.objectViewer
gcloud storage buckets add-iam-policy-binding gs://$LAKE --member=serviceAccount:$SA --role=roles/storage.objectUser
for role in roles/eventarc.eventReceiver roles/run.invoker; do
  gcloud projects add-iam-policy-binding $PROJECT --member=serviceAccount:$SA --role=$role
done
# Cloud Storage publishes the upload events
gcloud projects add-iam-policy-binding $PROJECT --role=roles/pubsub.publisher \
  --member=serviceAccount:$(gcloud storage service-agent --project=$PROJECT)
```

## 3. Write the function

`main.py`:

```python
"""Appends each CSV or Parquet file that lands in the landing bucket to a Timelake table."""

import io
import os

import functions_framework
import pyarrow.csv as csv
import pyarrow.parquet as pq
import timelake
from google.cloud import storage

gcs = storage.Client()
lake = timelake.Lake(os.environ["TIMELAKE_WAREHOUSE"])
table = lake.table(os.environ["TIMELAKE_TABLE"])


def read(name, body):
    return pq.read_table(io.BytesIO(body)) if name.endswith(".parquet") else csv.read_csv(io.BytesIO(body))


@functions_framework.cloud_event
def ingest(event):
    bucket, name = event.data["bucket"], event.data["name"]
    body = gcs.bucket(bucket).blob(name).download_as_bytes()
    # The object name is the batch id: a redelivered event loads nothing twice.
    print(name, table.append(read(name, body), batch_id=name))


@functions_framework.http
def maintain(request):
    for name in lake.tables():
        print(name, lake.table(name).maintain())
    return "ok"
```

`requirements.txt`:

```
functions-framework
google-cloud-storage
timelake
```

Events are delivered at least once, and `--retry` below retries failed calls. With the object name as the batch id, a repeated event is skipped. So give every upload a unique name, such as `gateway-7/20260105T1000.csv`, and send corrections as new files.

## 4. Deploy it

```bash
gcloud functions deploy timelake-ingest --gen2 --region=$REGION --runtime=python313 \
  --source=. --entry-point=ingest --trigger-bucket=$LANDING --retry \
  --service-account=$SA --trigger-service-account=$SA \
  --memory=1Gi --timeout=120s --max-instances=4 \
  --set-env-vars=TIMELAKE_WAREHOUSE=gs://$LAKE/warehouse,TIMELAKE_TABLE=iot.readings
```

On Cloud Run, Timelake gets the service account's credentials from the metadata server. Commits to one table happen one at a time: when two instances commit together, one retries. `--max-instances=4` keeps those retries rare. Fewer, larger files ingest faster than many small ones.

## 5. Send a file and query it

```bash
cat > readings.csv <<'EOF'
time,device_id,temp,humidity
2026-01-05T10:00:00Z,pump-1,61.2,40
2026-01-05T10:00:00Z,pump-2,58.9,42
EOF
gcloud storage cp readings.csv gs://$LANDING/gateway-1/20260105T1000.csv

gcloud functions logs read timelake-ingest --gen2 --region=$REGION --limit=5    # the append result
timelake latest iot.readings
```

## 6. Schedule maintenance (optional)

Each append already merges small files and removes duplicates. An hourly `maintain` also sorts each finished day into one file and deletes expired files:

```bash
gcloud functions deploy timelake-maintain --gen2 --region=$REGION --runtime=python313 \
  --source=. --entry-point=maintain --trigger-http --no-allow-unauthenticated \
  --service-account=$SA --memory=2Gi --timeout=900s \
  --set-env-vars=TIMELAKE_WAREHOUSE=gs://$LAKE/warehouse,TIMELAKE_TABLE=iot.readings
URL=$(gcloud functions describe timelake-maintain --gen2 --region=$REGION --format='value(serviceConfig.uri)')
gcloud scheduler jobs create http timelake-maintain --location=$REGION --schedule="0 * * * *" \
  --uri=$URL --http-method=POST --oidc-service-account-email=$SA --oidc-token-audience=$URL
```

## Cost

Each append sends about 7 writes and 2 reads to the lake bucket. Cloud Storage charges writes as Class A and reads as Class B operations. [Storage & configuration](/docs/storage#requests-and-cost) lists the requests per append and per query. To pay less, have gateways send fewer, larger files.
