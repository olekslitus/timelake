# Google Cloud

On Google Cloud, Timelake runs inside Cloud Run functions and keeps its tables in a Cloud Storage bucket. Data reaches the functions in one of several ways, depending on how your devices send it. Every design below appends to the same table from the same source folder, so you can start with one and add another later.

| Design | Devices send | Visible to queries after | Fits |
| --- | --- | --- | --- |
| [Files to Cloud Storage](#design-1-files-to-cloud-storage) | CSV, Parquet, or JSON files | each upload | gateways that buffer readings and upload every few minutes |
| [Pub/Sub to Cloud Storage](#design-2-pubsub-to-cloud-storage) | Pub/Sub messages | the file interval (1 to 10 minutes) | many small senders; Pub/Sub does the batching |
| [Pub/Sub, pulled every minute](#design-3-pubsub-pulled-every-minute) | Pub/Sub messages | about a minute | a steady message stream with no extra files in between |

**Which to start with.** If your gateways can write files, use design 1: it has the fewest parts, and each file is one commit. If devices send single readings, use design 2, which turns a minute of messages into one file and so one commit. Use design 3 when you'd rather not keep landing files, or need data within about a minute.

Then [scheduled checks](#scheduled-checks-on-recent-data) read recent data and alert, and [maintenance](#maintenance) runs every hour. [Other designs](#other-designs) covers MQTT devices, per-message triggers, and backfills.

Timelake hasn't been tested on Cloud Storage yet ([Limitations](/docs/limitations)). It reaches Cloud Storage through the same storage library as S3, and commits use Cloud Storage's generation preconditions.

## Cloud Storage or BigQuery tables for Apache Iceberg

Google Cloud has its own way to keep Iceberg tables in your bucket: BigQuery tables for Apache Iceberg.

|  | Cloud Storage bucket, with Timelake | BigQuery tables for Apache Iceberg |
| --- | --- | --- |
| Data | Parquet and Iceberg metadata in your bucket | Parquet in your bucket; BigQuery keeps the table's metadata |
| Writers | Timelake (CLI, Python, Rust) | BigQuery: DML, load jobs, the Storage Write API, Pub/Sub BigQuery subscriptions |
| Compaction | In the writer, after appends; `maintain` for a full pass | BigQuery's storage optimization, billed as compute |
| Readers | Timelake, DuckDB, and other engines that open Iceberg tables by path | BigQuery; other engines read an exported metadata snapshot, which can lag streamed data |
| Time-series features | Latest values, deduplication, rollups, retention by time | Plain Iceberg, queried with BigQuery SQL |
| Runs on | Any object store, or local disk | Google Cloud only |

Choose BigQuery tables if your queries already run in BigQuery. Choose Timelake on Cloud Storage for frequent small appends that need fast queries straight away, for time-series queries, or to keep the same setup on other clouds. Files written into a BigQuery-managed table by anything other than BigQuery are not tracked, so Timelake can't write into one.

## Shared setup

Do this once for every design. The commands use the `gcloud` CLI and the `timelake` command ([install](/docs/quick-start#1-install)).

```bash
export PROJECT=$(gcloud config get-value project) REGION=us-central1
export LANDING=${PROJECT}-timelake-landing LAKE=${PROJECT}-timelake-lake
export SA=timelake@${PROJECT}.iam.gserviceaccount.com
gcloud services enable run.googleapis.com cloudbuild.googleapis.com artifactregistry.googleapis.com \
  eventarc.googleapis.com pubsub.googleapis.com cloudscheduler.googleapis.com secretmanager.googleapis.com
```

timelake create iot.readings --schema "time:timestamptz,device_id:string,temp:double,humidity:int" \

### The function code

In a new folder, one `main.py` has an entry point per design. Each Cloud Run function picks its own with `--function`.

```python
"""Timelake on Cloud Run functions: append from Cloud Storage or Pub/Sub; maintain the tables; check recent data."""

import datetime as dt
import io
import json
import os
import time
import urllib.request

import functions_framework
import pyarrow as pa
import pyarrow.csv as csv
import pyarrow.parquet as pq
import timelake
from google.cloud import pubsub_v1, storage

gcs = storage.Client()
subscriber = pubsub_v1.SubscriberClient()
lake = timelake.Lake(os.environ["TIMELAKE_WAREHOUSE"])
table = lake.table(os.environ["TIMELAKE_TABLE"])


def read_messages(payloads):
    """Readings from JSON messages, each one reading or a list of readings."""
    rows = []
    for payload in payloads:
        try:
            message = json.loads(payload)
        except ValueError:
            print("skipped, not JSON:", payload[:200])
            continue
        rows.extend(message if isinstance(message, list) else [message])
    return pa.Table.from_pylist(rows)


def read_file(name, body):
    if name.endswith(".parquet"):
        return pq.read_table(io.BytesIO(body))
    if name.endswith(".csv"):
        return csv.read_csv(io.BytesIO(body))
    return read_messages(body.splitlines())  # one JSON message per line, as Pub/Sub writes them


@functions_framework.cloud_event
def ingest_gcs(event):
    bucket, name = event.data["bucket"], event.data["name"]
    body = gcs.bucket(bucket).blob(name).download_as_bytes()
    data = read_file(name, body)
    # The object name is the batch id: a redelivered event loads nothing twice.
    if data.num_rows:
        print(name, table.append(data, batch_id=name))


@functions_framework.http
def pull(request):
    """Pulls the waiting messages for up to 30 seconds, appends them in one commit, then acknowledges them."""
    subscription = os.environ["SUBSCRIPTION"]
    payloads, ack_ids, deadline = [], [], time.monotonic() + 30
    while time.monotonic() < deadline:
        response = subscriber.pull(subscription=subscription, max_messages=1000, timeout=10)
        if not response.received_messages:
            break
        for received in response.received_messages:
            payloads.append(received.message.data)
            ack_ids.append(received.ack_id)
    data = read_messages(payloads)
    if data.num_rows:
        print(len(payloads), "messages", table.append(data))
    for i in range(0, len(ack_ids), 1000):
        subscriber.acknowledge(subscription=subscription, ack_ids=ack_ids[i : i + 1000])
    return "ok"


@functions_framework.http
def maintain(request):
    for name in lake.tables():
        print(name, lake.table(name).maintain())
    return "ok"


@functions_framework.http
def check(request):
    """Alerts on pumps running hot over the last 10 minutes and on pumps silent for 15."""
    hot = lake.sql("""
        SELECT device_id, avg(temp) AS avg_temp, max(temp) AS max_temp
        FROM iot.readings
        WHERE time > now() - INTERVAL '10 minutes'
        GROUP BY device_id
        HAVING avg(temp) > 80
    """).to_pylist()
    now = dt.datetime.now(dt.timezone.utc)
    latest = lake.latest("iot.readings").to_pylist()
    silent = [r["device_id"] for r in latest if now - r["time"] > dt.timedelta(minutes=15)]
    print({"hot": hot, "silent": silent})
    if hot or silent:
        text = "Timelake check\n" + json.dumps({"hot": hot, "silent": silent}, default=str, indent=2)
        urllib.request.urlopen(
            urllib.request.Request(
                os.environ["ALERT_WEBHOOK"],
                data=json.dumps({"text": text}).encode(),
                headers={"Content-Type": "application/json; charset=UTF-8"},
            )
        )
    return "ok"
```

`requirements.txt`:

```
functions-framework
google-cloud-pubsub
google-cloud-storage
timelake
```

Messages are JSON, one reading or a list of readings, with the table's columns:

```json
{"time": "2026-01-05T10:00:00Z", "device_id": "pump-1", "temp": 61.2, "humidity": 40}
```

### Two shell helpers

`run_function` deploys a Cloud Run function from the folder; `schedule` calls one on a schedule from Cloud Scheduler. Both work in bash and zsh.

```bash
run_function() {   # run_function <name> <entry point> [more gcloud run deploy options]
  name=$1 entry=$2; shift 2
  gcloud run deploy $name --source . --function $entry --base-image python313 --region $REGION \
    --service-account $SA --no-allow-unauthenticated --memory 1Gi --timeout 120 \
    --set-env-vars TIMELAKE_WAREHOUSE=gs://${LAKE}/warehouse,TIMELAKE_TABLE=iot.readings "$@"
}
schedule() {   # schedule <function> <cron>
  url=$(gcloud run services describe $1 --region $REGION --format='value(status.url)')
  gcloud scheduler jobs create http $1 --location $REGION --schedule "$2" --uri $url --http-method POST \
    --oidc-service-account-email $SA --oidc-token-audience $url
}
```

On Cloud Run, Timelake gets the service account's credentials from the metadata server.

**Retries and concurrency.** Eventarc and Pub/Sub deliver at least once. Where a batch has a stable name (an object name), it is the batch id, and a repeat is skipped. Batch ids are remembered while their commits are kept: by default the last hour, and at most 100 commits. Beyond that, and for pulled messages, deduplication keeps one row per device and time. Commits to one table happen one at a time: when two functions commit together, one retries. Each design caps its instances at a few, so those retries stay rare.

Gateways buffer readings and upload a file every few minutes. Each upload triggers the function. A separate landing bucket keeps the lake's own writes from triggering it. The landing bucket must be in the same region as the trigger.

```bash
gcloud storage buckets create gs://$LANDING --location=$REGION --uniform-bucket-level-access
gcloud storage buckets add-iam-policy-binding gs://$LANDING --member=serviceAccount:$SA --role=roles/storage.objectViewer
# Cloud Storage publishes the upload events
gcloud projects add-iam-policy-binding $PROJECT --role=roles/pubsub.publisher \
  --member=serviceAccount:$(gcloud storage service-agent --project=$PROJECT)

run_function timelake-gcs ingest_gcs --max-instances 4
gcloud eventarc triggers create timelake-gcs --location=$REGION --destination-run-service=timelake-gcs \
  --event-filters=type=google.cloud.storage.object.v1.finalized --event-filters=bucket=$LANDING \
  --service-account=$SA
```

Try it:

```bash
cat > readings.csv <<'EOF'
time,device_id,temp,humidity
2026-01-05T10:00:00Z,pump-1,61.2,40
2026-01-05T10:00:00Z,pump-2,58.9,42
EOF
gcloud storage cp readings.csv gs://$LANDING/gateway-1/20260105T1000.csv
gcloud run services logs read timelake-gcs --region=$REGION --limit=5
timelake latest iot.readings
```

Give every upload a unique name, such as the gateway and the time, and send corrections as new files: a name that was already loaded is skipped.

Devices publish readings to a topic. A Cloud Storage subscription writes the waiting messages to the landing bucket as one file per interval (1 to 10 minutes), one message per line. The function from design 1 appends each file, so each interval becomes one commit, however many devices publish. Set up design 1 first.

```bash
gcloud pubsub topics create timelake-readings
PUBSUB_AGENT=service-$(gcloud projects describe $PROJECT --format='value(projectNumber)')@gcp-sa-pubsub.iam.gserviceaccount.com
for role in roles/storage.objectCreator roles/storage.legacyBucketReader; do
  gcloud storage buckets add-iam-policy-binding gs://$LANDING --member=serviceAccount:$PUBSUB_AGENT --role=$role
done
gcloud pubsub subscriptions create timelake-files --topic=timelake-readings \
  --cloud-storage-bucket=$LANDING --cloud-storage-file-prefix=pubsub- --cloud-storage-file-suffix=.jsonl \
  --cloud-storage-max-duration=1m --cloud-storage-output-format=text
```

With text output, the files hold only the message bodies, which `read_file` reads as JSON lines. A longer `--cloud-storage-max-duration` means fewer, larger commits; `--cloud-storage-max-bytes` closes a file early when it gets large.

Try it:

```bash
gcloud pubsub topics publish timelake-readings \
  --message='{"time": "2026-01-05T10:05:00Z", "device_id": "pump-1", "temp": 62.0, "humidity": 41}'
```

From a device or gateway with the Pub/Sub client:

```python
import json

from google.cloud import pubsub_v1

publisher = pubsub_v1.PublisherClient()
topic = publisher.topic_path("my-project", "timelake-readings")
for r in readings:
    publisher.publish(topic, json.dumps(r).encode())
```

## Design 3: Pub/Sub, pulled every minute

<IngestFlow

Cloud Scheduler calls the `pull` function every minute. It pulls up to 1,000 messages at a time for up to 30 seconds, appends them all in one commit, and only then acknowledges them. If the function fails before the acknowledgement, Pub/Sub delivers the messages again.

```bash
gcloud pubsub topics create timelake-readings          # skip if design 2 created it
gcloud pubsub subscriptions create timelake-pull --topic=timelake-readings --ack-deadline=120
gcloud pubsub subscriptions add-iam-policy-binding timelake-pull --member=serviceAccount:$SA \
  --role=roles/pubsub.subscriber

run_function timelake-pull pull --max-instances 2
gcloud run services update timelake-pull --region $REGION \
  --update-env-vars SUBSCRIPTION=projects/${PROJECT}/subscriptions/timelake-pull
schedule timelake-pull "* * * * *"
```

The acknowledgement deadline (120 s) is longer than one run, so a message isn't delivered again while the function still holds it. Try it by publishing as in design 2; the reading appears in the table within a minute.

Why not trigger a function from each message? A Pub/Sub trigger calls the function once per message, and each call would be one commit. That suits a few messages a minute, not a fleet of devices.

## Scheduled checks on recent data

<IngestFlow
  nodes={[
    { label: "Cloud Scheduler", sub: "*/5 * * * *" },
    { label: "Cloud Run function", sub: "check", accent: true },
    { label: "Lake bucket", sub: "iot.readings" },
    { label: "Webhook", sub: "Google Chat, Slack" },
  ]}

/>

The `check` entry point runs every 5 minutes. It asks two questions of the table and posts to a chat webhook when either has an answer:

- Which pumps averaged above 80° over the last 10 minutes? A SQL query over recent data. The time filter skips every file whose time range lies outside the window, before any data is read.
- Which pumps have sent nothing for 15 minutes? `lake.latest()` answers from the last-value index, without scanning the table.

Google Chat and Slack incoming webhooks both accept the `{"text": …}` body it sends. The webhook URL is a secret, so it goes in Secret Manager:

```bash
printf '%s' 'https://chat.googleapis.com/v1/spaces/…' | gcloud secrets create timelake-alert-webhook --data-file=-
gcloud secrets add-iam-policy-binding timelake-alert-webhook --member=serviceAccount:$SA \
  --role=roles/secretmanager.secretAccessor

run_function timelake-check check
gcloud run services update timelake-check --region $REGION --update-secrets ALERT_WEBHOOK=timelake-alert-webhook:latest
schedule timelake-check "*/5 * * * *"
```

Change the SQL to check anything the table holds: a rate of change, a counter that stopped increasing, readings outside a band per site (join a devices table). Over longer windows, a [rollup](/docs/rollups) keeps the query small. A check that also wants a record of what it found can append its findings to another Timelake table.

## Maintenance

Each append already merges small files and removes duplicates. An hourly `maintain` also sorts each finished day into one file, applies retention, and deletes files no version needs:

```bash
run_function timelake-maintain maintain
gcloud run services update timelake-maintain --region $REGION --memory 2Gi --timeout 900
schedule timelake-maintain "0 * * * *"
```

## Other designs

- **Devices over MQTT.** Google Cloud IoT Core was retired in 2023, so there is no managed MQTT service to put in front. Run an MQTT broker (on GKE or a VM) with a bridge that publishes to the Pub/Sub topic, then use design 2 or 3.
- **A function per message.** An Eventarc or push trigger on the topic calls a function per message: simple, and fine for a few messages a minute. Beyond that, use design 2 or 3.
- **A long-running consumer.** For a stream busy enough to keep a puller running all the time, run the `pull` loop continuously on GKE or a VM, appending every few seconds.
- **Backfill.** Load history from a VM in the same region: `gcloud storage cp -r` the old files to disk, then `timelake import iot.readings ./history --batch-id backfill-2025`. Appends of history don't conflict with live ingestion.

## Cost

Each commit sends about 7 writes and 2 reads to the lake bucket; Cloud Storage charges writes as Class A and reads as Class B operations. At one commit a minute, that is about 10,000 writes a day. So the batching settings above (upload interval, file interval, pull schedule) are the main cost control. [Storage & configuration](/docs/storage#requests-and-cost) breaks the requests down. Pub/Sub charges per data volume, and Cloud Run bills for the time each function runs.
