# Vercel

On Vercel, Timelake runs inside a Python function, a FastAPI app, and keeps its tables in an S3-compatible bucket. Vercel Blob doesn't work as the store: Timelake can read a warehouse over HTTPS but needs the S3 API to write. This guide uses [Tigris](https://www.tigrisdata.com) and shows how to switch to S3 or R2. Every design below appends to the same table from the same project, so you can start with one and add another later.

| Design | Devices send | Visible to queries after | Fits |
| --- | --- | --- | --- |
| [HTTP, appended directly](#design-1-http-appended-directly) | JSON over HTTPS | each request | a few gateways, a few requests a minute |
| [Vercel Queues, pushed](#design-2-vercel-queues-pushed) | a batch of readings per HTTPS request | seconds | gateways that batch readings; bursts and retries |
| [Vercel Queues, drained by cron](#design-3-vercel-queues-drained-by-cron) | one reading per HTTPS request | up to a minute | many devices sending single readings |
| [Files, appended by cron](#design-4-files-appended-by-cron) | CSV, Parquet, or JSON files to the bucket | up to a minute | gateways that upload files with the S3 API |

**Which to choose.** If gateways batch readings, use design 2: the queue absorbs bursts and retries, and each batch becomes one commit. If devices send one reading at a time, use design 3, which turns a minute of messages into one commit. Use design 1 only for a handful of senders, and design 4 when gateways already upload files. Designs 3 and 4, the [scheduled checks](#scheduled-checks-on-recent-data), and hourly [maintenance](#maintenance) need cron jobs that run every few minutes, which the Pro plan allows. Hobby runs cron jobs at most once a day.

## Shared setup

Do this once for every design. The commands use the [Vercel CLI](https://vercel.com/docs/cli), the AWS CLI, and the `timelake` command ([install](/docs/quick-start#1-install)).

### The bucket and the table

In the [Tigris console](https://console.tigris.dev), create a bucket named `timelake` and an access key with Editor access to it. Tigris is also listed in the Vercel Marketplace; if you connect it that way, use the keys it gives you below. Then create the table from your machine:

```bash
export AWS_ACCESS_KEY_ID="<access key id>" AWS_SECRET_ACCESS_KEY="<secret access key>"
export AWS_ENDPOINT_URL=https://t3.storage.dev AWS_REGION=auto
export TIMELAKE_WAREHOUSE=s3://timelake/warehouse
timelake create iot.readings --schema "time:timestamptz,device_id:string,temp:double,humidity:int" \
  --time-column time --series-key device_id
```

Run `uv lock` to pin every dependency in `uv.lock`, which Vercel installs from. The packages take about 370 MB installed, within the 500 MB limit for a Python function.

`lake.py`:

```python
"""The Timelake table and the readers every route shares."""

import functools
import io
import os

import pyarrow as pa
import pyarrow.csv as csv
import pyarrow.json as pj
import pyarrow.parquet as pq
import timelake

# Vercel may set AWS_* variables of its own in functions; they aren't credentials for your store.
os.environ.pop("AWS_SESSION_TOKEN", None)


def store():
    return {
        "aws_access_key_id": os.environ["TIMELAKE_S3_ACCESS_KEY_ID"],
        "aws_secret_access_key": os.environ["TIMELAKE_S3_SECRET_ACCESS_KEY"],
        "aws_endpoint": os.environ["TIMELAKE_S3_ENDPOINT"],
        "aws_region": os.environ["TIMELAKE_S3_REGION"],
    }


# Opened on first use, not on import: Vercel imports the subscriber modules at build time.
@functools.cache
def lake():
    return timelake.Lake(os.environ["TIMELAKE_WAREHOUSE"], storage_options=store())


@functools.cache
def table():
    return lake().table(os.environ["TIMELAKE_TABLE"])


def read_file(name, body):
    if name.endswith(".parquet"):
        return pq.read_table(io.BytesIO(body))
    if name.endswith(".csv"):
        return csv.read_csv(io.BytesIO(body))
    return pj.read_json(io.BytesIO(body))  # newline-delimited JSON


def read_messages(messages):
    """Readings from JSON values, each one reading or a list of readings."""
    rows = []
    for message in messages:
        rows.extend(message if isinstance(message, list) else [message])
    return pa.Table.from_pylist(rows)
```

The store's credentials come from variables named `TIMELAKE_S3_*` and are passed to Timelake directly. Vercel's docs note that `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, and `AWS_SESSION_TOKEN` may appear in functions without being usable credentials, so the code doesn't rely on them.

`app.py` (each design below explains its routes):

```python
"""Timelake on Vercel: HTTP intake, queue producers, and the cron jobs."""

import asyncio
import datetime as dt
import functools
import json
import os
import time
import urllib.request

import boto3
from fastapi import Body, FastAPI, Header, HTTPException, Request
from vercel.queue import ALL_DEPLOYMENTS, QueueClient, send

from lake import lake, read_file, read_messages, store, table

app = FastAPI()
polled = QueueClient(region="iad1", deployment=ALL_DEPLOYMENTS)


def require(request: Request, secret: str):
    if request.headers.get("authorization") != f"Bearer {os.environ[secret]}":
        raise HTTPException(status_code=401)


# Design 1: append each request.
@app.post("/api/readings")
def append_readings(request: Request, readings: list[dict] | dict = Body(), idempotency_key: str | None = Header(None)):
    require(request, "INGEST_TOKEN")
    # A retried request with the same Idempotency-Key header loads nothing twice.
    return table().append(read_messages([readings]), batch_id=idempotency_key)


# Design 2: one queue message per request, appended by the subscriber in queues/readings.py.
@app.post("/api/batches")
async def enqueue_batch(request: Request):
    require(request, "INGEST_TOKEN")
    return {"messageId": await send("gateway-batches", await request.json())}


# Design 3: many small messages, drained in batches by a cron job.
@app.post("/api/readings/queue")
async def enqueue_reading(request: Request):
    require(request, "INGEST_TOKEN")
    return {"messageId": await polled.send("readings", await request.json())}


@app.get("/api/cron/drain")
async def drain(request: Request):
    require(request, "CRON_SECRET")
    messages, deadline = [], time.monotonic() + 50
    while time.monotonic() < deadline and len(messages) < 10_000:
        claimed = [d.accept() async for d in polled.poll("readings", "timelake", limit=10, lease_duration=120)]
        if not claimed:
            break
        messages += claimed
    if not messages:
        return {"messages": 0}
    # Redelivered messages come back in other batches, so a batch has no stable id; deduplication
    # keeps one row per device and time instead.
    result = await asyncio.to_thread(table().append, read_messages(m.payload for m in messages))
    for m in messages:
        await polled.acknowledge(m)
    return {"messages": len(messages), **result}


@functools.cache
def s3():
    s = store()
    return boto3.client(
        "s3",
        endpoint_url=s["aws_endpoint"],
        region_name=s["aws_region"],
        aws_access_key_id=s["aws_access_key_id"],
        aws_secret_access_key=s["aws_secret_access_key"],
    )


# Design 4: files uploaded to landing/, appended by a cron job.
@app.get("/api/cron/landing")
def landing(request: Request):
    require(request, "CRON_SECRET")
    bucket, loaded = os.environ["TIMELAKE_LANDING_BUCKET"], {}
    for page in s3().get_paginator("list_objects_v2").paginate(Bucket=bucket, Prefix="landing/"):
        for obj in page.get("Contents", []):
            key = obj["Key"]
            body = s3().get_object(Bucket=bucket, Key=key)["Body"].read()
            # The object key is the batch id: if the job stops before the delete, the next run skips the file.
            loaded[key] = table().append(read_file(key, body), batch_id=key)
            s3().delete_object(Bucket=bucket, Key=key)
    return loaded


@app.get("/api/cron/check")
def check(request: Request):
    """Alert on pumps running hot over the last 10 minutes and on pumps silent for 15."""
    require(request, "CRON_SECRET")
    hot = lake().sql("""
        SELECT device_id, avg(temp) AS avg_temp, max(temp) AS max_temp
        FROM iot.readings
        WHERE time > now() - INTERVAL '10 minutes'
        GROUP BY device_id
        HAVING avg(temp) > 80
    """).to_pylist()
    now = dt.datetime.now(dt.timezone.utc)
    latest = lake().latest("iot.readings").to_pylist()
    silent = [r["device_id"] for r in latest if now - r["time"] > dt.timedelta(minutes=15)]
    if hot or silent:
        body = json.dumps({"text": f"Timelake check: hot {hot}, silent {silent}"}, default=str).encode()
        alert = urllib.request.Request(os.environ["ALERT_WEBHOOK_URL"], body, {"content-type": "application/json"})
        urllib.request.urlopen(alert, timeout=10)
    return {"hot": hot, "silent": silent}


@app.get("/api/cron/maintain")
def maintain(request: Request):
    require(request, "CRON_SECRET")
    return {name: lake().table(name).maintain() for name in lake().tables()}
```

Messages are JSON, one reading or a list of readings, with the table's columns:

```json
{"time": "2026-01-05T10:00:00Z", "device_id": "pump-1", "temp": 61.2, "humidity": 40}
```

`vercel.json` (on Hobby, keep only the `maintain` job, scheduled once a day):

```json
{
  "$schema": "https://openapi.vercel.sh/vercel.json",
  "functions": { "app.py": { "maxDuration": 120 } },
  "crons": [
    { "path": "/api/cron/drain", "schedule": "* * * * *" },
    { "path": "/api/cron/landing", "schedule": "* * * * *" },
    { "path": "/api/cron/check", "schedule": "*/5 * * * *" },
    { "path": "/api/cron/maintain", "schedule": "0 * * * *" }
  ]
}
```

The configuration is `vercel.json` rather than `vercel.ts` because `vercel.ts` needs a Node.js package (`@vercel/config`) in an otherwise Python project. Vercel sends `CRON_SECRET` as a bearer token on every cron request, and `require` checks it.

```bash
printf %s "$INGEST_TOKEN" | vercel env add INGEST_TOKEN production
export CRON_SECRET=$(openssl rand -hex 32)
printf %s "$CRON_SECRET" | vercel env add CRON_SECRET production
printf %s https://hooks.example.com/your-webhook | vercel env add ALERT_WEBHOOK_URL production
vercel deploy --prod
export URL="https://<your project>.vercel.app"
```

**Another store.** For S3, set `TIMELAKE_S3_ENDPOINT` to `https://s3.<region>.amazonaws.com`, `TIMELAKE_S3_REGION` to the bucket's region, and use an IAM user's keys. For R2, use `https://<account id>.r2.cloudflarestorage.com` and `auto`, and run the conditional-write check in the [Cloudflare guide](/docs/quick-start/cloudflare) first.

**Retries and concurrency.** HTTP clients, queues, and cron jobs may all deliver the same data more than once. Where data has a stable name (an `Idempotency-Key` header, a queue message id, a file key), it is the batch id, and a repeat is skipped. Batch ids are remembered while their commits are kept: by default the last hour, and at most 100 commits. Beyond that, deduplication keeps one row per device and time. Commits to one table happen one at a time: when two functions commit together, one retries.

## Design 1: HTTP, appended directly

The route appends each request body as one commit. It is the shortest path, but each request is a commit: keep it to a few requests a minute per table. At one request per second, the store's requests alone cost about $3 a day, and commits, which happen one at a time, begin to wait on each other. A request body can be up to 4.5 MB.

Try it:

```bash
curl -X POST $URL/api/readings -H "authorization: Bearer $INGEST_TOKEN" -H "idempotency-key: gateway-1-000001" \
  -H "content-type: application/json" \
  -d '[{"time": "2026-01-05T10:00:00Z", "device_id": "pump-1", "temp": 61.2, "humidity": 40}]'
```

Send the same `Idempotency-Key` when retrying a request; a new batch gets a new key.

The intake route puts each request on a queue topic and answers at once. Vercel then calls the subscriber once per message, at most two at a time, and retries a message until the subscriber returns without an error. Each message is one commit, so this fits gateways that send a batch of readings every few seconds or minutes.

`queues/readings.py`:

```python
"""Design 2: append each gateway batch from the queue, one commit per message."""

import asyncio

from vercel.queue import Message, subscribe

from lake import read_messages, table


@subscribe(topic="gateway-batches", max_concurrency=2)
async def append_batch(message: Message[list[dict[str, object]]]) -> None:
    # A redelivered message keeps its id, so it loads nothing twice.
    data = read_messages([message.payload])
    print(await asyncio.to_thread(table().append, data, batch_id=message.message_id))
```

The `[[tool.vercel.subscribers]]` entry in `pyproject.toml` makes Vercel build this module into its own queue-triggered function. Messages are kept for 24 hours by default.

Try it:

```bash
curl -X POST $URL/api/batches -H "authorization: Bearer $INGEST_TOKEN" -H "content-type: application/json" \
  -d '[{"time": "2026-01-05T10:05:00Z", "device_id": "pump-1", "temp": 62.0, "humidity": 41},
       {"time": "2026-01-05T10:05:00Z", "device_id": "pump-2", "temp": 59.4, "humidity": 43}]'
```

## Design 3: Vercel Queues, drained by cron

When every device sends its own readings, one commit per message would be too many. Here nothing is pushed: once a minute a cron job claims messages, up to 10 per request, for at most 50 seconds or 10,000 messages. It appends them all in one commit, then acknowledges them. If the append fails, nothing is acknowledged, and the messages return to the queue when their 120-second lease runs out.

Two settings on the `polled` client matter. Messages can only be received in the region they were sent to, so the client names a fixed region (`iad1`). And topics are separate per deployment by default; `ALL_DEPLOYMENTS` lets the cron job of a new deployment drain what an earlier deployment received.

Try it:

```bash
curl -X POST $URL/api/readings/queue -H "authorization: Bearer $INGEST_TOKEN" -H "content-type: application/json" \
  -d '{"time": "2026-01-05T10:10:00Z", "device_id": "pump-3", "temp": 60.1, "humidity": 42}'
```

The reading reaches the table at the next minute.

Gateways upload files under `landing/` in the bucket with any S3 client, using an access key of their own (create one in the Tigris console). Once a minute a cron job lists the files, appends each one with its key as the batch id, and deletes it. Give every file a unique key, such as the gateway and the time, and send corrections as new files.

Try it:

```bash
cat > readings.csv <<'EOF'
time,device_id,temp,humidity
2026-01-05T10:15:00Z,pump-1,64.0,40
EOF
aws s3 cp readings.csv s3://timelake/landing/gateway-1-20260105T1015.csv
```

## Scheduled checks on recent data

<IngestFlow
  nodes={[

    { label: "Tigris bucket", sub: "iot.readings" },
    { label: "Webhook", sub: "Slack, Teams, …" },

  edges={["GET", "query", "alert"]}
/>

The `check` route runs every 5 minutes and asks two questions of the table:

- Which pumps averaged above 80° over the last 10 minutes? A SQL query over recent data. The time filter skips every file whose time range lies outside the window, before any data is read.
- Which pumps have sent nothing for 15 minutes? `lake.latest()` answers from the last-value index, without scanning the table.

When either has an answer, it posts a JSON message with a `text` field to `ALERT_WEBHOOK_URL`, the format Slack and Teams incoming webhooks accept. Change the SQL to check anything the table holds; over longer windows, a [rollup](/docs/rollups) keeps the query small.

Vercel doesn't retry a failed cron run, and may occasionally run one twice or let two overlap. Every job here is safe to repeat: the drain claims each message once, the landing job skips files already loaded, and a repeated check sends the alert again.

## Maintenance

Each append already merges small files and removes duplicates. The hourly `maintain` job also sorts each finished day into one file, applies retention, and deletes files no version needs. To run it by hand:

```bash
curl $URL/api/cron/maintain -H "authorization: Bearer $CRON_SECRET"
```

## Other designs

- **A long-running consumer.** Vercel Queues can also be polled from outside Vercel. A container on Fly.io, a VM, or a Kubernetes job can run `poll_and_handle` and append every few seconds, holding the table open between appends.
- **Dashboards.** A Next.js app can read the lake with the [TypeScript client](/docs/typescript), which reads warehouses served over HTTPS.

## Cost

Each commit sends about 7 writes and 2 reads to the bucket. Tigris prices writes like S3 ($0.005 per 1,000) and reads at $0.0005 per 1,000. At one commit per second that is about $3 a day in requests; at one per minute, as in designs 3 and 4, about 5 cents. [Storage & configuration](/docs/storage#requests-and-cost) breaks the requests down. On Vercel, functions bill for active CPU time and invocations. Queues bill per operation: sending, receiving, acknowledging, and each push, counted per 4 KiB of message, with idempotency keys and `max_concurrency` pushes at twice the rate. Hobby includes the first million queue operations.
