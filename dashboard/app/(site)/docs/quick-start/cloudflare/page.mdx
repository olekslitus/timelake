# Cloudflare

On Cloudflare, Timelake keeps its tables in an R2 bucket. A Worker takes uploads from devices, and a writer script appends them to the table. The writer is native code, so it can't run inside a Worker (the WebAssembly build of Timelake only reads). It runs from cron on any Linux host with Python, such as a small VM, and talks to R2 through R2's S3-compatible API.

| Design | Devices send | Visible to queries after | Fits |
| --- | --- | --- | --- |
| [Files to R2](#design-1-files-to-r2) | CSV or Parquet files over HTTPS | the next writer run (a minute) | gateways that buffer readings and upload every few minutes |
| [Queue with a pull consumer](#design-2-queue-with-a-pull-consumer) | JSON readings over HTTPS | the next writer run (a minute) | devices that send single readings or small lists |
| [R2 event notifications](#design-3-r2-event-notifications) | files over HTTPS or the S3 API | the next writer run (a minute) | many files, or gateways that upload to R2 directly |

**Which to choose.** Start with design 1 if your gateways already batch readings into files: it needs no queue. Choose design 2 when devices send readings one at a time. Choose design 3 over design 1 when the landing area holds many files at once: the writer learns about each file from a notification instead of listing the bucket every minute.

Then [scheduled checks](#scheduled-checks-on-recent-data) read recent data and alert, and [maintenance](#maintenance) runs every hour. [Other designs](#other-designs) covers running the writer in a Cloudflare Container, and Basin Pipelines.

## R2 or Basin Catalog

Cloudflare offers two ways to keep Iceberg tables in R2. Timelake writes the first.

|  | R2 bucket, with Timelake | Basin Catalog (formerly R2 Data Catalog) |
| --- | --- | --- |
| What it is | Ordinary objects: Parquet data and Iceberg metadata, written by the Timelake library | A managed Iceberg catalog built into an R2 bucket, with an Iceberg REST interface |
| Commits | A conditional write of the next metadata file | Through the REST catalog |
| Compaction | In the writer, after appends; `maintain` for a full pass | Opt-in per catalog or table, to a target file size (default 128 MB) |
| Snapshot expiry | In the writer, by age and count | Opt-in per catalog or table, by age and count |
| Writers | Timelake (CLI, Python, Rust) | Iceberg engines such as Spark and PyIceberg; Basin Pipelines (Parquet, a commit every 60 s or more) |
| Readers | Timelake, DuckDB, and other engines that open Iceberg tables by path | Spark, PyIceberg, Snowflake, and other engines through the REST interface; Basin SQL |
| Time-series features | Latest values, deduplication, rollups, retention by time | Plain Iceberg |
| Runs on | Any object store, or local disk | Cloudflare only |

Choose Basin Catalog if your writers and readers are Iceberg engines that connect through a REST catalog, or if Basin Pipelines already carries your data. Choose Timelake on R2 for frequent small appends that need fast queries straight away, for time-series queries, or to keep the same setup on other clouds. Timelake can't yet write through an Iceberg REST catalog; that is planned.

## Shared setup

Do this once for every design. Timelake hasn't been tested on R2 yet ([Limitations](/docs/limitations)), and the probe below checks the one feature it depends on. The commands use [Wrangler](https://developers.cloudflare.com/workers/wrangler/), the AWS CLI (for the probe), [uv](https://docs.astral.sh/uv/), and the `timelake` command ([install](/docs/quick-start#1-install)).

### The bucket and the credentials

```bash
npx wrangler r2 bucket create timelake
```

In the Cloudflare dashboard, open **R2 → Manage API tokens → Create API token**, choose **Object Read & Write**, and limit it to the `timelake` bucket. Note the access key ID, the secret access key, and your account ID. Timelake and the writer use them as S3 credentials. Keep them in a file that cron can read too:

```bash
mkdir -p ~/timelake && cd ~/timelake
cat > timelake.env <<'EOF'
export AWS_ACCESS_KEY_ID="<access key id>" AWS_SECRET_ACCESS_KEY="<secret access key>" AWS_REGION=auto
export AWS_ENDPOINT="https://<account id>.r2.cloudflarestorage.com"
export TIMELAKE_WAREHOUSE=s3://timelake/lake TIMELAKE_TABLE=iot.readings R2_BUCKET=timelake
EOF
. ./timelake.env
```

### Conditional writes and the table

Each commit is a put-if-absent. The second `put-object` must fail with `PreconditionFailed`:

```bash
echo probe > probe.txt
aws s3api put-object --endpoint-url $AWS_ENDPOINT --bucket timelake --key probe.txt --body probe.txt --if-none-match '*'
aws s3api put-object --endpoint-url $AWS_ENDPOINT --bucket timelake --key probe.txt --body probe.txt --if-none-match '*'
aws s3api delete-object --endpoint-url $AWS_ENDPOINT --bucket timelake --key probe.txt

timelake create iot.readings --schema "time:timestamptz,device_id:string,temp:double,humidity:int" \
  --time-column time --series-key device_id
```

### The writer

One script, `~/timelake/writer.py`, has a mode per design. Cron runs it with `uv`, which installs `timelake` and `boto3` on first use.

```python
"""Timelake writer for Cloudflare: appends from R2 or a Queue, and checks recent data.

Usage: python writer.py files | queue | events | check
"""

import base64
import datetime as dt
import io
import json
import os
import sys
import urllib.request

import boto3
import pyarrow as pa
import pyarrow.csv as csv
import pyarrow.json as pj
import pyarrow.parquet as pq
import timelake

BUCKET = os.environ["R2_BUCKET"]
r2 = boto3.client("s3", endpoint_url=os.environ["AWS_ENDPOINT"], region_name="auto")
lake = timelake.Lake(os.environ["TIMELAKE_WAREHOUSE"])
table = lake.table(os.environ["TIMELAKE_TABLE"])


def read_file(name, body):
    if name.endswith(".parquet"):
        return pq.read_table(io.BytesIO(body))
    if name.endswith(".csv"):
        return csv.read_csv(io.BytesIO(body))
    return pj.read_json(io.BytesIO(body))  # newline-delimited JSON


def read_messages(payloads):
    """Readings from JSON messages, each one reading or a list of readings."""
    rows = []
    for payload in payloads:
        try:
            message = json.loads(payload)
        except ValueError:
            print("skipped, not JSON:", payload[:200])
            continue
        rows.extend(message if isinstance(message, list) else [message])
    return pa.Table.from_pylist(rows)


def queues_api(queue_id, action, body):
    account = os.environ["CF_ACCOUNT_ID"]
    request = urllib.request.Request(
        f"https://api.cloudflare.com/client/v4/accounts/{account}/queues/{queue_id}/messages/{action}",
        data=json.dumps(body).encode(),
        headers={"Authorization": f"Bearer {os.environ['CF_QUEUES_TOKEN']}", "Content-Type": "application/json"},
    )
    with urllib.request.urlopen(request) as response:
        return json.load(response)["result"]


def pull(queue_id, limit):
    """Up to `limit` messages, 100 per request, leased for 2 minutes."""
    messages = []
    while len(messages) < limit:
        batch = queues_api(queue_id, "pull", {"batch_size": 100, "visibility_timeout_ms": 120_000})["messages"]
        messages += batch
        if len(batch) < 100:
            break
    return messages


def ack(queue_id, messages):
    for i in range(0, len(messages), 100):
        leases = [{"lease_id": m["lease_id"]} for m in messages[i : i + 100]]
        queues_api(queue_id, "ack", {"acks": leases, "retries": []})


def append_file(key):
    try:
        body = r2.get_object(Bucket=BUCKET, Key=key)["Body"].read()
    except r2.exceptions.NoSuchKey:
        print(key, "already appended and deleted")
        return
    # The object key is the batch id: if the writer stops before the delete, the next run skips the file.
    print(key, table.append(read_file(key, body), batch_id=key))
    r2.delete_object(Bucket=BUCKET, Key=key)


def files():
    for page in r2.get_paginator("list_objects_v2").paginate(Bucket=BUCKET, Prefix="landing/"):
        for obj in page.get("Contents", []):
            append_file(obj["Key"])


def queue():
    queue_id = os.environ["READINGS_QUEUE_ID"]
    messages = pull(queue_id, limit=1000)
    data = read_messages(base64.b64decode(m["body"]) for m in messages)
    if data.num_rows:
        # Lease ids change on every delivery, so a batch has no stable id. Messages delivered
        # again after a failed ack are kept once by deduplication.
        print(len(messages), "messages", table.append(data))
    ack(queue_id, messages)


def events():
    queue_id = os.environ["EVENTS_QUEUE_ID"]
    messages = pull(queue_id, limit=100)
    for m in messages:
        append_file(json.loads(base64.b64decode(m["body"]))["object"]["key"])
    ack(queue_id, messages)


def check():
    """Alert on pumps running hot over the last 10 minutes and on pumps silent for 15."""
    hot = lake.sql("""
        SELECT device_id, avg(temp) AS avg_temp, max(temp) AS max_temp
        FROM iot.readings
        WHERE time > now() - INTERVAL '10 minutes'
        GROUP BY device_id
        HAVING avg(temp) > 80
    """).to_pylist()
    now = dt.datetime.now(dt.timezone.utc)
    latest = lake.latest("iot.readings").to_pylist()
    silent = [r["device_id"] for r in latest if now - r["time"] > dt.timedelta(minutes=15)]
    print({"hot": hot, "silent": silent})
    if hot or silent:
        text = json.dumps({"hot": hot, "silent": silent}, default=str)
        request = urllib.request.Request(
            os.environ["ALERT_WEBHOOK"],
            data=json.dumps({"text": text}).encode(),
            headers={"Content-Type": "application/json"},
        )
        urllib.request.urlopen(request)


if __name__ == "__main__":
    {"files": files, "queue": queue, "events": events, "check": check}[sys.argv[1]]()
```

### The Worker

One Worker takes uploads for designs 1 and 2. `src/index.js`:

```js
// Intake for gateways and devices:
//   PUT  /files/<name>.csv (or .parquet)  stores the file under landing/ in R2 (design 1)
//   POST /readings                        puts a JSON reading, or a list of readings, on a queue (design 2)
const NAME = /^[\w.-]+\.(csv|parquet)$/

export default {
  async fetch(request, env) {
    if (request.headers.get("authorization") !== `Bearer ${env.INGEST_TOKEN}`) {
      return new Response("unauthorized", { status: 401 })
    }
    const path = new URL(request.url).pathname
    if (request.method === "PUT" && path.startsWith("/files/") && NAME.test(path.slice(7))) {
      // The gateway names each file (gateway id + sequence number), so a retried upload
      // overwrites the same object and the writer loads it once.
      const key = `landing/${path.slice(7)}`
      await env.LAKE.put(key, await request.arrayBuffer())
      return new Response(`${key}\n`, { status: 201 })
    }
    if (request.method === "POST" && path === "/readings" && env.READINGS) {
      const bytes = await request.arrayBuffer()
      if (bytes.byteLength > 128_000) return new Response("over 128 KB: split it", { status: 413 })
      let body
      try {
        body = JSON.parse(new TextDecoder().decode(bytes))
      } catch {
        return new Response("not JSON", { status: 400 })
      }
      await env.READINGS.send(body)
      return new Response("queued\n", { status: 202 })
    }
    return new Response("PUT /files/<name>.csv or POST /readings", { status: 400 })
  },
}
```

`wrangler.jsonc`:

```json
{
  "name": "timelake-intake",
  "main": "src/index.js",
  "compatibility_date": "2026-10-01",
  "r2_buckets": [{ "binding": "LAKE", "bucket_name": "timelake" }]
}
```

```bash
openssl rand -hex 32 | npx wrangler secret put INGEST_TOKEN     # note the token for the devices
npx wrangler deploy
```

**Retries and concurrency.** Every path here can deliver the same data twice: a device retries an upload, or a message comes back after its lease runs out. Files have a stable name, which is the batch id, so a repeat is skipped. Batch ids are remembered while their commits are kept: by default the last hour, and at most 100 commits. Beyond that, and for queue messages, deduplication keeps one row per device and time. Each append is one commit, and commits to one table happen one at a time. `flock -n` in the cron lines below skips a run while the previous one is still going, so each mode has one writer.

Gateways upload files through the Worker. Every minute the writer lists `landing/`, appends each file, and deletes it. The cron line (`crontab -e`):

```
* * * * * cd $HOME/timelake && . ./timelake.env && flock -n files.lock $HOME/.local/bin/uv run --with timelake --with boto3 writer.py files >> writer.log 2>&1
```

Try it:

```bash
cat > readings.csv <<'EOF'
time,device_id,temp,humidity
2026-01-05T10:00:00Z,pump-1,61.2,40
2026-01-05T10:00:00Z,pump-2,58.9,42
EOF
curl -X PUT --data-binary @readings.csv -H "authorization: Bearer <token>" \
  "https://timelake-intake.<your subdomain>.workers.dev/files/gateway-1-20260105T1000.csv"
uv run --with timelake --with boto3 writer.py files      # or wait for cron
timelake latest iot.readings
```

Give every file a unique name, such as the gateway and a sequence number, and send corrections as new files: a name that was already loaded is skipped.

## Design 2: Queue with a pull consumer

<IngestFlow
  nodes={[
    { label: "Devices", sub: "JSON readings" },
    { label: "Worker", sub: "POST /readings" },
    { label: "Queue" },
    { label: "Writer", sub: "writer.py queue", accent: true },
    { label: "R2 lake/", sub: "Iceberg tables" },
  ]}
  edges={["HTTPS", "send", "pull, ack", "commit"]}
/>

Devices post readings to the Worker, which puts each request on a Cloudflare Queue. The queue has an HTTP pull consumer instead of a consumer Worker: every minute the writer pulls up to 1,000 messages over the Cloudflare API (100 per request), appends them as one commit, and acknowledges them. Messages it doesn't acknowledge within the 2-minute lease come back. After 5 failed deliveries a message moves to a dead-letter queue.

```bash
npx wrangler queues create timelake-readings-dlq
npx wrangler queues create timelake-readings
npx wrangler queues consumer http add timelake-readings \
  --batch-size 100 --message-retries 5 --visibility-timeout-secs 120 --dead-letter-queue timelake-readings-dlq
npx wrangler queues info timelake-readings      # note the queue ID
```

Create an API token with **Account → Queues → Edit** (pulling and acknowledging need write access), and add it to `timelake.env`:

```bash
cat >> timelake.env <<'EOF'
export CF_ACCOUNT_ID="<account id>" CF_QUEUES_TOKEN="<queues api token>" READINGS_QUEUE_ID="<queue id>"
EOF
```

Bind the queue to the Worker in `wrangler.jsonc`, then run `npx wrangler deploy` again:

```json
{
  "name": "timelake-intake",
  "main": "src/index.js",
  "compatibility_date": "2026-10-01",
  "r2_buckets": [{ "binding": "LAKE", "bucket_name": "timelake" }],
  "queues": { "producers": [{ "binding": "READINGS", "queue": "timelake-readings" }] }
}
```

The cron line:

```
* * * * * cd $HOME/timelake && . ./timelake.env && flock -n queue.lock $HOME/.local/bin/uv run --with timelake --with boto3 writer.py queue >> writer.log 2>&1
```

Try it:

```bash
curl -X POST -H "authorization: Bearer <token>" "https://timelake-intake.<your subdomain>.workers.dev/readings" \
  --data '[{"time": "2026-01-05T10:05:00Z", "device_id": "pump-1", "temp": 62.0, "humidity": 41},
           {"time": "2026-01-05T10:05:00Z", "device_id": "pump-2", "temp": 59.4, "humidity": 43}]'
```

A message holds up to 128 KB. For readings sooner than once a minute, run `writer.py queue` in a loop with a short sleep instead of from cron.

## Design 3: R2 event notifications

<IngestFlow
  nodes={[
    { label: "Gateways", sub: "files" },
    { label: "R2 landing/" },
    { label: "Queue", sub: "object-create events" },
    { label: "Writer", sub: "writer.py events", accent: true },
    { label: "R2 lake/", sub: "Iceberg tables" },
  ]}
  edges={["upload", "notify", "pull, ack", "commit"]}
/>

R2 puts a message on a queue for every object created under `landing/`. The writer pulls those messages, appends each named file, and deletes it, so it never lists the bucket. Files can arrive through the Worker from design 1, or straight through R2's S3 API from gateways that have their own R2 token. Use this mode instead of `writer.py files`, not alongside it.

```bash
npx wrangler queues create timelake-events
npx wrangler queues consumer http add timelake-events --batch-size 100 --message-retries 5 --visibility-timeout-secs 120
npx wrangler r2 bucket notification create timelake --event-type object-create --queue timelake-events --prefix landing/
npx wrangler queues info timelake-events      # note the queue ID
cat >> timelake.env <<'EOF'
export EVENTS_QUEUE_ID="<queue id>"
EOF
```

The writer's own writes go under `lake/` and its deletes aren't `object-create` events, so they don't trigger notifications. The cron line:

```
* * * * * cd $HOME/timelake && . ./timelake.env && flock -n events.lock $HOME/.local/bin/uv run --with timelake --with boto3 writer.py events >> writer.log 2>&1
```

Try it with an upload through the Worker, as in design 1. A notification delivered twice finds the file already appended and deleted, and is skipped.

## Scheduled checks on recent data

<IngestFlow
  nodes={[
    { label: "cron", sub: "every 5 minutes" },
    { label: "Writer", sub: "writer.py check", accent: true },
    { label: "R2 lake/", sub: "iot.readings" },

  ]}

/>

The `check` mode runs every 5 minutes. It asks two questions of the table and posts to a webhook when either has an answer:

- Which pumps averaged above 80° over the last 10 minutes? A SQL query over recent data. The time filter skips every file whose time range lies outside the window, before any data is read.
- Which pumps have sent nothing for 15 minutes? `lake.latest()` answers from the last-value index, without scanning the table.

```bash
cat >> timelake.env <<'EOF'
export ALERT_WEBHOOK="<incoming webhook url>"
EOF
```

```
*/5 * * * * cd $HOME/timelake && . ./timelake.env && $HOME/.local/bin/uv run --with timelake --with boto3 writer.py check >> check.log 2>&1
```

The body is `{"text": "…"}`, which a Slack incoming webhook takes as is; change it for other services. Change the SQL to check anything the table holds: a rate of change, a counter that stopped increasing, or readings outside a band per site (join a devices table). Over longer windows, a [rollup](/docs/rollups) keeps the query small.

## Maintenance

Each append already merges small files and removes duplicates. An hourly `timelake maintain` also sorts each finished day into one file, applies retention, and deletes files no version needs:

```
0 * * * * cd $HOME/timelake && . ./timelake.env && $HOME/.cargo/bin/timelake maintain >> maintain.log 2>&1
```

## Other designs

- **The writer in a Cloudflare Container.** A Worker's Cron Trigger can start a container on a schedule ([Cron Container example](https://developers.cloudflare.com/containers/examples/cron)). Built from an image with `timelake` and `writer.py`, and with internet access turned on so it can reach R2 and the Queues API, it replaces the host and its cron. The example doesn't queue overlapping runs, so keep the interval longer than a run.
- **A long-running writer.** For lower latency, run the queue mode in a loop as a service on the host, pulling every few seconds.
- **Basin Pipelines.** Pipelines take records over HTTP or from a Worker and write Parquet into Basin Catalog tables, with a commit every 60 seconds or more. That gives plain Iceberg tables in R2 without a writer host; see [R2 or Basin Catalog](#r2-or-basin-catalog) for the trade-offs.

## Cost

R2 charges per million writes and per million reads, and nothing for data read out of it. Each commit sends about 7 writes and 2 reads to the bucket; [Storage & configuration](/docs/storage#requests-and-cost) breaks the requests down. Each file in designs 1 and 3 adds an upload, a read, a delete, and in design 1 a share of the minute's list. Queues bill per 64 KB written, read, or deleted, so a delivered message usually costs 3 operations: Workers Free includes 10,000 operations a day, and Workers Paid 1 million a month, then $0.40 per million. Workers bill per request. Fewer, larger uploads and messages cost less on every line.
