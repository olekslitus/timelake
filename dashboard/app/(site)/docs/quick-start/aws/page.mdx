# AWS

On AWS, Timelake runs inside Lambda functions and keeps its tables in an S3 bucket. Data reaches the functions in one of several ways, depending on how your devices send it. Every design below appends to the same table with the same container image, so you can start with one and add another later.

| Design | Devices send | Visible to queries after | Fits |
| --- | --- | --- | --- |
| [Files to S3](#design-1-files-to-s3) | CSV, Parquet, or JSON files | each upload | gateways that buffer readings and upload every few minutes |
| [Kinesis Data Streams](#design-2-kinesis-data-streams) | records through the AWS SDK | the batching window (seconds) | steady, high-volume streams; replay; order per device |
| [SQS](#design-3-sqs) | messages through the AWS SDK or HTTP | the batching window (seconds) | bursty or low volume; the simplest queue |
| [IoT Core](#design-4-iot-core) | MQTT messages | the batching window (seconds) | devices with certificates that speak MQTT |
| [Data Firehose](#design-5-data-firehose) | records through the AWS SDK | the buffer interval (60 s or more) | many small senders; AWS does the batching |

Then [scheduled checks](#scheduled-checks-on-recent-data) read recent data and alert, and [maintenance](#maintenance) runs every hour. [Other designs](#other-designs) lists a long-running consumer, HTTP intake, and backfills.

## S3 or S3 Tables

AWS offers two places to keep Iceberg tables. Timelake writes to the first.

|  | S3 general-purpose bucket, with Timelake | S3 Tables (table buckets) |
| --- | --- | --- |
| What it is | Ordinary objects: Parquet data and Iceberg metadata, written by the Timelake library | A bucket type for Iceberg tables, with an AWS-managed catalog |
| Commits | A conditional write of the next metadata file | Through the S3 Tables API (an Iceberg REST endpoint) |
| Compaction | In the writer, after appends; `maintain` for a full pass | Managed by AWS in the background (2.4–2.6 hours after ingest in our run) |
| Writers | Timelake (CLI, Python, Rust) | Any Iceberg client: Spark, PyIceberg, Firehose |
| Readers | Timelake, DuckDB, and other engines that open Iceberg tables by path | Athena, Redshift, and EMR through the Glue Data Catalog; Spark, PyIceberg, and DuckDB through the REST endpoint |
| Time-series features | Latest values, deduplication, rollups, retention by time | Plain Iceberg |
| Runs on | Any object store, or local disk | AWS only |
| You pay for | S3 storage and requests, Lambda time | Table-bucket storage and requests, plus monitoring and compaction fees |

Measured on the same data ([TSBS IoT](/benchmarks/tsbs-iot), 1,728 five-minute commits, laptop to us-east-2, [details](https://github.com/polythings/timelake/blob/main/bench/results/S3.md)):

| | Timelake on S3 | S3 Tables |
| --- | ---: | ---: |
| Query right after ingest | 1.5 s, 65 requests | 21.6 s, 1,547 requests |
| Query after S3 Tables' compaction (2.4–2.6 h later) | 1.2 s | 2.4 s |
| Median commit | 0.48 s | 1.46 s |

Choose S3 Tables if your queries go through Athena or Redshift, your writes come in large batches, and waiting hours for compaction is acceptable. Choose Timelake on S3 for frequent small appends that need fast queries straight away, for time-series queries, or to keep the same setup on other clouds. Timelake can't yet write into a table bucket or register its tables in Glue: both are planned through an Iceberg REST catalog.

## Shared setup

Do this once for every design. The commands use the AWS CLI, Docker, and the `timelake` command ([install](/docs/quick-start#1-install)).

```bash
export AWS_REGION=us-east-2
export ACCOUNT=$(aws sts get-caller-identity --query Account --output text)
export LANDING=$ACCOUNT-timelake-landing LAKE=$ACCOUNT-timelake-lake
export REPO=$ACCOUNT.dkr.ecr.$AWS_REGION.amazonaws.com/timelake
```

Timelake reads credentials from the `AWS_*` environment variables, not from `~/.aws/config`. To use a profile or an SSO login on your machine, export its credentials first:

```bash
eval "$(aws configure export-credentials --format env)"
```

### The lake bucket and the table

```bash
aws s3 mb s3://$LAKE
export TIMELAKE_WAREHOUSE=s3://$LAKE/warehouse
timelake create iot.readings --schema "time:timestamptz,device_id:string,temp:double,humidity:int" \
  --time-column time --series-key device_id
```

### The function code

One `handler.py` has an entry point per design. Each function picks its own with `--image-config Command=handler.<name>`.

```python
"""Timelake on AWS Lambda: append from S3, Kinesis, or SQS; maintain the tables; check recent data."""

import base64
import datetime as dt
import io
import json
import os
from urllib.parse import unquote_plus

import boto3
import pyarrow as pa
import pyarrow.csv as csv
import pyarrow.json as pj
import pyarrow.parquet as pq
import timelake

s3 = boto3.client("s3")
lake = timelake.Lake(os.environ["TIMELAKE_WAREHOUSE"])
table = lake.table(os.environ["TIMELAKE_TABLE"])


def read_file(name, body):
    if name.endswith(".parquet"):
        return pq.read_table(io.BytesIO(body))
    if name.endswith(".csv"):
        return csv.read_csv(io.BytesIO(body))
    return pj.read_json(io.BytesIO(body))  # newline-delimited JSON, as Firehose writes it


def read_messages(payloads):
    """Readings from JSON messages, each one reading or a list of readings."""
    rows = []
    for payload in payloads:
        try:
            message = json.loads(payload)
        except ValueError:
            print("skipped, not JSON:", payload[:200])
            continue
        rows.extend(message if isinstance(message, list) else [message])
    return pa.Table.from_pylist(rows)


def ingest_s3(event, context):
    for record in event["Records"]:
        bucket = record["s3"]["bucket"]["name"]
        key = unquote_plus(record["s3"]["object"]["key"])
        body = s3.get_object(Bucket=bucket, Key=key)["Body"].read()
        # The object key is the batch id: a redelivered event loads nothing twice.
        print(key, table.append(read_file(key, body), batch_id=key))


def ingest_kinesis(event, context):
    records = event["Records"]
    data = read_messages(base64.b64decode(r["kinesis"]["data"]) for r in records)
    # The shard and the sequence numbers name the batch: a retried batch loads nothing twice.
    batch_id = f"{records[0]['eventID']}-{records[-1]['kinesis']['sequenceNumber']}"
    if data.num_rows:
        print(batch_id, table.append(data, batch_id=batch_id))


def ingest_sqs(event, context):
    # SQS regroups messages when it redelivers them, so a batch has no stable id. Deduplication
    # keeps one row per device and time instead.
    data = read_messages(r["body"] for r in event["Records"])
    if data.num_rows:
        print(len(event["Records"]), "messages", table.append(data))


def maintain(event, context):
    for name in lake.tables():
        print(name, lake.table(name).maintain())


def check(event, context):
    """Alert on pumps running hot over the last 10 minutes and on pumps silent for 15."""
    hot = lake.sql("""
        SELECT device_id, avg(temp) AS avg_temp, max(temp) AS max_temp
        FROM iot.readings
        WHERE time > now() - INTERVAL '10 minutes'
        GROUP BY device_id
        HAVING avg(temp) > 80
    """).to_pylist()
    now = dt.datetime.now(dt.timezone.utc)
    latest = lake.latest("iot.readings").to_pylist()
    silent = [r["device_id"] for r in latest if now - r["time"] > dt.timedelta(minutes=15)]
    print({"hot": hot, "silent": silent})
    if hot or silent:
        boto3.client("sns").publish(
            TopicArn=os.environ["ALERT_TOPIC"],
            Subject="Timelake check",
            Message=json.dumps({"hot": hot, "silent": silent}, default=str, indent=2),
        )
```

Messages are JSON, one reading or a list of readings, with the table's columns:

```json
{"time": "2026-01-05T10:00:00Z", "device_id": "pump-1", "temp": 61.2, "humidity": 40}
```

`Dockerfile`:

```dockerfile
FROM public.ecr.aws/lambda/python:3.13-arm64
RUN pip install --no-cache-dir timelake boto3
COPY handler.py ${LAMBDA_TASK_ROOT}/
CMD ["handler.ingest_s3"]
```

The functions are deployed as a container image because `timelake` and `pyarrow` together are larger than the 250 MB limit for a zip upload ([#98](https://github.com/polythings/timelake/issues/98)).

### The image and the role

```bash
aws ecr create-repository --repository-name timelake
aws ecr get-login-password | docker login --username AWS --password-stdin ${REPO%%/*}
docker build --platform linux/arm64 --provenance=false -t ${REPO}:latest .
docker push ${REPO}:latest

aws iam create-role --role-name timelake --assume-role-policy-document '{
  "Version": "2012-10-17",
  "Statement": [{"Effect": "Allow", "Principal": {"Service": "lambda.amazonaws.com"}, "Action": "sts:AssumeRole"}]
}'
aws iam attach-role-policy --role-name timelake \
  --policy-arn arn:aws:iam::aws:policy/service-role/AWSLambdaBasicExecutionRole
aws iam put-role-policy --role-name timelake --policy-name lake --policy-document '{
  "Version": "2012-10-17",
  "Statement": [
    {"Effect": "Allow", "Action": ["s3:GetObject", "s3:PutObject", "s3:DeleteObject", "s3:AbortMultipartUpload"],
     "Resource": "arn:aws:s3:::'$LAKE'/*"},
    {"Effect": "Allow", "Action": "s3:ListBucket", "Resource": "arn:aws:s3:::'$LAKE'"}
  ]
}'
```

A shell function creates each Lambda function from the image (it works in bash and zsh):

```bash
lambda_function() {   # lambda_function <name> <entry point> [more create-function options]
  name=$1 entry=$2; shift 2
  aws lambda create-function --function-name $name --package-type Image --code ImageUri=${REPO}:latest \
    --image-config Command=handler.$entry --architectures arm64 --role arn:aws:iam::${ACCOUNT}:role/timelake \
    --memory-size 1024 --timeout 120 \
    --environment "Variables={TIMELAKE_WAREHOUSE=s3://$LAKE/warehouse,TIMELAKE_TABLE=iot.readings}" "$@"
  aws lambda wait function-active-v2 --function-name $name
}
```

Lambda supplies credentials and the region in environment variables, which Timelake reads.

**Retries and concurrency.** Every event source here delivers at least once. Where a batch has a stable name (an S3 key, a Kinesis sequence range), it is the batch id, and a repeat is skipped. Batch ids are remembered while their commits are kept: by default the last hour, and at most 100 commits. Beyond that, and for SQS, deduplication keeps one row per device and time. Commits to one table happen one at a time: when two functions commit together, one retries. Each design caps its concurrency at a few functions, so those retries stay rare.

Gateways buffer readings and upload a file every few minutes. Each upload triggers the function. A separate landing bucket keeps the lake's own writes from triggering it.

```bash
aws s3 mb s3://$LANDING
aws iam put-role-policy --role-name timelake --policy-name landing --policy-document '{
  "Version": "2012-10-17",
  "Statement": [{"Effect": "Allow", "Action": "s3:GetObject", "Resource": "arn:aws:s3:::'$LANDING'/*"}]
}'
lambda_function timelake-s3 ingest_s3
aws lambda put-function-concurrency --function-name timelake-s3 --reserved-concurrent-executions 4
aws lambda add-permission --function-name timelake-s3 --statement-id landing-bucket \
  --action lambda:InvokeFunction --principal s3.amazonaws.com \
  --source-arn arn:aws:s3:::$LANDING --source-account $ACCOUNT
aws s3api put-bucket-notification-configuration --bucket $LANDING --notification-configuration '{
  "LambdaFunctionConfigurations": [{
    "LambdaFunctionArn": "arn:aws:lambda:'$AWS_REGION:$ACCOUNT':function:timelake-s3",
    "Events": ["s3:ObjectCreated:*"]
  }]
}'
```

Try it:

```bash
cat > readings.csv <<'EOF'
time,device_id,temp,humidity
2026-01-05T10:00:00Z,pump-1,61.2,40
2026-01-05T10:00:00Z,pump-2,58.9,42
EOF
aws s3 cp readings.csv s3://$LANDING/gateway-1/20260105T1000.csv
aws logs tail /aws/lambda/timelake-s3 --since 5m
timelake latest iot.readings
```

Give every upload a unique key, such as the gateway and the time, and send corrections as new files: a key that was already loaded is skipped. Events beyond the concurrency limit wait in Lambda's queue.

## Design 2: Kinesis Data Streams

<IngestFlow
  nodes={[
    { label: "Devices", sub: "PutRecords" },
    { label: "Kinesis stream" },
    { label: "Lambda", sub: "ingest_kinesis", accent: true },
    { label: "S3 lake bucket", sub: "Iceberg tables" },
  ]}
  edges={["SDK", "batch", "commit"]}
/>

Devices put records on a stream, with the device id as the partition key so each device's readings stay in order. Lambda reads each shard in batches: one function per shard at a time, one commit per batch. The stream keeps records for 24 hours by default, so a failed batch is retried and a broken function can catch up.

```bash
aws kinesis create-stream --stream-name timelake-readings --stream-mode-details StreamMode=ON_DEMAND
aws iam attach-role-policy --role-name timelake \
  --policy-arn arn:aws:iam::aws:policy/service-role/AWSLambdaKinesisExecutionRole
lambda_function timelake-kinesis ingest_kinesis
aws lambda create-event-source-mapping --function-name timelake-kinesis \
  --event-source-arn arn:aws:kinesis:$AWS_REGION:${ACCOUNT}:stream/timelake-readings \
  --starting-position LATEST --batch-size 10000 --maximum-batching-window-in-seconds 30 \
  --maximum-retry-attempts 10
```

`--maximum-batching-window-in-seconds` sets the trade-off: a longer window means fewer, larger commits and fewer requests, and data reaches queries later. A batch that still fails after 10 retries is dropped; add `--destination-config` with an SQS queue to keep it. An on-demand stream starts with 4 shards, so up to 4 functions commit at once.

Try it:

```bash
aws kinesis put-record --stream-name timelake-readings --partition-key pump-1 --cli-binary-format raw-in-base64-out \
  --data '{"time": "2026-01-05T10:05:00Z", "device_id": "pump-1", "temp": 62.0, "humidity": 41}'
```

From a device or gateway with the AWS SDK, send readings in batches:

```python
import json

import boto3

kinesis = boto3.client("kinesis")
kinesis.put_records(
    StreamName="timelake-readings",
    Records=[{"Data": json.dumps(r), "PartitionKey": r["device_id"]} for r in readings],
)
```

## Design 3: SQS

<IngestFlow
  nodes={[
    { label: "Devices", sub: "SendMessage" },
    { label: "SQS queue" },
    { label: "Lambda", sub: "ingest_sqs", accent: true },
    { label: "S3 lake bucket", sub: "Iceberg tables" },
  ]}
  edges={["SDK / HTTP", "batch", "commit"]}
/>

Devices send messages to a queue, each one reading or a list of readings. Lambda collects up to 10,000 messages or 30 seconds' worth per call and commits them at once. A message that keeps failing moves to a dead-letter queue after 5 tries.

```bash
DLQ_URL=$(aws sqs create-queue --queue-name timelake-readings-dlq --query QueueUrl --output text)
DLQ_ARN=$(aws sqs get-queue-attributes --queue-url $DLQ_URL --attribute-names QueueArn \
  --query Attributes.QueueArn --output text)
cat > queue.json <<EOF
{"VisibilityTimeout": "720", "RedrivePolicy": "{\"deadLetterTargetArn\":\"$DLQ_ARN\",\"maxReceiveCount\":\"5\"}"}
EOF
QUEUE_URL=$(aws sqs create-queue --queue-name timelake-readings --attributes file://queue.json \
  --query QueueUrl --output text)

aws iam attach-role-policy --role-name timelake \
  --policy-arn arn:aws:iam::aws:policy/service-role/AWSLambdaSQSQueueExecutionRole
lambda_function timelake-sqs ingest_sqs
aws lambda create-event-source-mapping --function-name timelake-sqs \
  --event-source-arn arn:aws:sqs:$AWS_REGION:${ACCOUNT}:timelake-readings \
  --batch-size 10000 --maximum-batching-window-in-seconds 30 --scaling-config MaximumConcurrency=2
```

The visibility timeout (720 s) is six times the function timeout, as AWS recommends, so a message isn't handed out again while a function still holds it. `MaximumConcurrency=2` caps the functions committing at once.

Try it:

```bash
aws sqs send-message --queue-url $QUEUE_URL \
  --message-body '[{"time": "2026-01-05T10:10:00Z", "device_id": "pump-1", "temp": 63.1, "humidity": 41},
                   {"time": "2026-01-05T10:10:00Z", "device_id": "pump-2", "temp": 60.2, "humidity": 44}]'
```

Devices without the AWS SDK can send over HTTPS: an API Gateway HTTP API has a built-in SQS integration (`SQS-SendMessage`) that puts each request body on the queue. Give the route an authorizer, such as a JWT authorizer, so only your devices can send.

## Design 4: IoT Core

<IngestFlow
  nodes={[

Devices with IoT Core certificates publish readings over MQTT to `devices/<device id>/readings`. A topic rule adds the device id from the topic and puts each message on the Kinesis stream from design 2, so the rest is the same. (A rule can send to the SQS queue from design 3 instead.) Registering devices and their certificates is covered in the [IoT Core docs](https://docs.aws.amazon.com/iot/latest/developerguide/iot-gs.html).

```bash
aws iam create-role --role-name timelake-iot-rule --assume-role-policy-document '{
  "Version": "2012-10-17",
  "Statement": [{"Effect": "Allow", "Principal": {"Service": "iot.amazonaws.com"}, "Action": "sts:AssumeRole"}]
}'
aws iam put-role-policy --role-name timelake-iot-rule --policy-name kinesis --policy-document '{
  "Version": "2012-10-17",
  "Statement": [{"Effect": "Allow", "Action": "kinesis:PutRecord",
                 "Resource": "arn:aws:kinesis:'$AWS_REGION:$ACCOUNT':stream/timelake-readings"}]
}'
cat > rule.json <<EOF
{
  "sql": "SELECT *, topic(2) AS device_id FROM 'devices/+/readings'",
  "awsIotSqlVersion": "2016-03-23",
  "actions": [{"kinesis": {
    "streamName": "timelake-readings",
    "partitionKey": "\${topic(2)}",
    "roleArn": "arn:aws:iam::${ACCOUNT}:role/timelake-iot-rule"
  }}]
}
EOF
aws iot create-topic-rule --rule-name timelake_readings --topic-rule-payload file://rule.json
```

Try it, publishing as a device would:

```bash
aws iot-data publish --topic devices/pump-1/readings --cli-binary-format raw-in-base64-out \
  --endpoint-url https://$(aws iot describe-endpoint --endpoint-type iot:Data-ATS --query endpointAddress --output text) \
  --payload '{"time": "2026-01-05T10:15:00Z", "temp": 64.0, "humidity": 40}'
```

## Design 5: Data Firehose

<IngestFlow
  nodes={[
    { label: "Devices", sub: "PutRecordBatch" },

Firehose collects records from many senders and writes them to the landing bucket as one file per buffer interval. The function from design 1 appends each file, so each interval becomes one commit, however many devices send. Set up design 1 first.

```bash
aws iam create-role --role-name timelake-firehose --assume-role-policy-document '{
  "Version": "2012-10-17",
  "Statement": [{"Effect": "Allow", "Principal": {"Service": "firehose.amazonaws.com"}, "Action": "sts:AssumeRole"}]
}'
aws iam put-role-policy --role-name timelake-firehose --policy-name landing --policy-document '{
  "Version": "2012-10-17",
  "Statement": [
    {"Effect": "Allow", "Action": ["s3:PutObject", "s3:AbortMultipartUpload"], "Resource": "arn:aws:s3:::'$LANDING'/*"},
    {"Effect": "Allow", "Action": ["s3:GetBucketLocation", "s3:ListBucket", "s3:ListBucketMultipartUploads"],
     "Resource": "arn:aws:s3:::'$LANDING'"}
  ]
}'
aws firehose create-delivery-stream --delivery-stream-name timelake-readings --delivery-stream-type DirectPut \
  --extended-s3-destination-configuration '{
    "RoleARN": "arn:aws:iam::'$ACCOUNT':role/timelake-firehose",
    "BucketARN": "arn:aws:s3:::'$LANDING'",
    "Prefix": "firehose/",
    "FileExtension": ".jsonl",
    "BufferingHints": {"IntervalInSeconds": 60, "SizeInMBs": 64},
    "ProcessingConfiguration": {"Enabled": true, "Processors": [{"Type": "AppendDelimiterToRecord"}]}
  }'
```

`AppendDelimiterToRecord` puts each record on its own line, which `read_file` reads as JSON lines. A longer buffer interval (up to 900 s) means fewer, larger commits.

Try it:

```bash
aws firehose put-record --delivery-stream-name timelake-readings --cli-binary-format raw-in-base64-out \
  --record '{"Data": "{\"time\": \"2026-01-05T10:20:00Z\", \"device_id\": \"pump-2\", \"temp\": 61.0, \"humidity\": 43}"}'
```

Firehose can also write into S3 Tables directly. Through Timelake, the same data gets the time-series layout and is queryable as soon as each file is appended.

## Scheduled checks on recent data

<IngestFlow
  nodes={[
    { label: "EventBridge", sub: "rate(5 minutes)" },
    { label: "Lambda", sub: "check", accent: true },
    { label: "S3 lake bucket", sub: "iot.readings" },
    { label: "SNS topic", sub: "email, SMS, chat" },
  ]}

/>

The `check` entry point runs every 5 minutes. It asks two questions of the table and publishes to an SNS topic when either has an answer:

- Which pumps averaged above 80° over the last 10 minutes? A SQL query over recent data. The time filter skips every file whose time range lies outside the window, before any data is read.
- Which pumps have sent nothing for 15 minutes? `lake.latest()` answers from the last-value index, without scanning the table.

```bash
TOPIC=$(aws sns create-topic --name timelake-alerts --query TopicArn --output text)
aws sns subscribe --topic-arn $TOPIC --protocol email --notification-endpoint you@example.com   # confirm the email
aws iam put-role-policy --role-name timelake --policy-name alerts --policy-document '{
  "Version": "2012-10-17",
  "Statement": [{"Effect": "Allow", "Action": "sns:Publish", "Resource": "'$TOPIC'"}]
}'
lambda_function timelake-check check
aws lambda update-function-configuration --function-name timelake-check \
  --environment "Variables={TIMELAKE_WAREHOUSE=s3://$LAKE/warehouse,TIMELAKE_TABLE=iot.readings,ALERT_TOPIC=$TOPIC}"

aws events put-rule --name timelake-check --schedule-expression "rate(5 minutes)"
aws lambda add-permission --function-name timelake-check --statement-id every-5-minutes \
  --action lambda:InvokeFunction --principal events.amazonaws.com \
  --source-arn arn:aws:events:$AWS_REGION:${ACCOUNT}:rule/timelake-check
aws events put-targets --rule timelake-check \
  --targets Id=1,Arn=arn:aws:lambda:$AWS_REGION:${ACCOUNT}:function:timelake-check
```

Change the SQL to check anything the table holds: a rate of change, a counter that stopped increasing, readings outside a band per site (join a devices table). Over longer windows, a [rollup](/docs/rollups) keeps the query small. A check that also wants a record of what it found can append its findings to another Timelake table.

## Maintenance

Each append already merges small files and removes duplicates. An hourly `maintain` also sorts each finished day into one file, applies retention, and deletes files no version needs:

```bash
lambda_function timelake-maintain maintain
aws lambda update-function-configuration --function-name timelake-maintain --memory-size 2048 --timeout 900
aws events put-rule --name timelake-maintain --schedule-expression "rate(1 hour)"
aws lambda add-permission --function-name timelake-maintain --statement-id hourly \
  --action lambda:InvokeFunction --principal events.amazonaws.com \
  --source-arn arn:aws:events:$AWS_REGION:${ACCOUNT}:rule/timelake-maintain
aws events put-targets --rule timelake-maintain \
  --targets Id=1,Arn=arn:aws:lambda:$AWS_REGION:${ACCOUNT}:function:timelake-maintain
```

## Other designs

- **A long-running consumer.** For a stream busy enough to keep a function running all the time, run the same code in a loop on ECS Fargate or EC2: poll SQS or read Kinesis, append every few seconds. It holds the table open between appends, and a container has no 250 MB package limit.
- **Lambda behind API Gateway, appending directly.** Simple, but every request becomes a commit. Fine for a handful of requests a minute. Beyond that, put a queue in between (design 3).
- **Backfill.** Load history from an EC2 instance in the same region: `aws s3 sync` the old files to disk, then `timelake import iot.readings ./history --batch-id backfill-2025`. Appends of history don't conflict with live ingestion. [Settings](/docs/settings) covers partition size for old data.

## Cost

Each commit sends about 7 PUTs and 2 GETs to the lake bucket. At one commit per second that is about $3 a day in S3 requests; at one per minute, about 5 cents. So the batching settings above (upload interval, batching window, buffer interval) are the main cost control. [Storage & configuration](/docs/storage#requests-and-cost) breaks the requests down. Kinesis, SQS, IoT Core, and Firehose have their own per-message or per-GB prices. Lambda bills for the seconds each function runs.
