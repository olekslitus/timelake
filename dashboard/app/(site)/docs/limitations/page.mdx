# Limitations

## Known limitations in v0

- **No REST catalog.** Tables are found by path (Hadoop-catalog layout). Engines that only speak the Iceberg REST protocol can’t attach yet.
- **Freshness is per commit.** Data is visible when its append commits; there is no hot tier or write-ahead log for sub-commit freshness.
- **No deletes.** Row-level deletes, the delete audit trail, and GDPR erasure are designed but not built. Retention drops whole partitions only.
- **No schema evolution.** The schema is fixed at creation.
- **Duplicates until compaction, outside Timelake.** The Timelake reader (CLI, Python, Rust) skips older copies of a row when reading; DuckDB, other Iceberg readers, and the TypeScript client see them until compaction removes them.
- **Rollups are one level, from the raw table.** No rollups of rollups, percentiles, or time-weighted averages in a rollup, and a query is only routed to a rollup with the same bucket width and grouping. Rollups don't see deletes (there are none yet). See [Rollups](/docs/rollups#not-yet).
- **In-memory compaction.** A partition is merged in memory; size the chunk interval so partitions fit.
- **Planning cache.** A process reuses a table version it loaded within the last second for query planning (its own commits are always visible).
- **Replaced files linger.** Files removed by compaction are deleted when the snapshots that reference them expire: at least an hour later by default, and inline expiry waits until about 20 extra snapshots have piled up.
- **Benchmarks are narrow.** One dataset (TSBS IoT). The AWS S3 runs were made from a laptop, so their latency includes the trip to the region; runs from inside AWS are next.
- **Tested storage.** Local disk, RustFS, AWS S3, and S3 Express One Zone (correctness only). GCS, Azure, and R2 use the same code paths but haven’t been tested yet.
