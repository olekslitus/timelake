# Codebase tour

What lives where, which technologies are used and why, and how a write and a query flow through the code. Paths are relative to the repository root. For the design behind it, see `SPEC.md`; for the on-disk format, see [Architecture](/docs/architecture).

## The big picture

```text
            your code
   ┌───────────┼──────────────┬──────────────────┐
   │           │              │                  │
 timelake    Python         Rust             browser / Node / serverless
  (CLI)    (timelake-py)   (use the crate)       │
   └───────────┼──────────────┘           @timelake/client (TypeScript)
               │                                 │
        crates/timelake  (the engine)     crates/timelake-wasm (read-only)
               │                                 │
               └──────── crates/timelake-format ─┘   shared rules
                                 │
                 object storage: Iceberg metadata + Parquet files
```

- **One engine.** All writing and full SQL happen in `crates/timelake`. The CLI and the Python package are thin layers over it.
- **A second, small reader for JavaScript.** The engine depends on DataFusion and Tokio, which are too large for a browser. `crates/timelake-wasm` reimplements just the reading needed for time-series queries (latest values, time ranges, time buckets). The rules both must agree on live in `crates/timelake-format`.
- **The website** uses the client package to read the demo data, and the CLI for local SQL.

## The engine, file by file

`crates/timelake/src`, about 2,700 lines. Read them in this order:

| File | What it does |
| --- | --- |
| `lib.rs` | The public API: `Lake`, `Table`, `Session`, options and results. |
| `storage.rs` | Opens the right object store for a URL (`s3://`, `gs://`, `az://`, `https://`, local). Provides read, write, `write_if_absent` (the conditional write), list and delete. Also adapts the store to iceberg-rust's file interface. |
| `lake.rs` | The catalog. `Lake` is a warehouse; `Table` is one version of a table. `create_table` writes `v1.metadata.json`; `table()` finds the current version (version hint, then check the next one); `files()` lists live data files from the manifests. Caches manifests, which never change once written. |
| `write.rs` | Turns Arrow batches into Parquet: `align_batch` (match the schema), `sort_and_split` (sort by partition, series, time), `writer_properties` (compression, encodings, statistics), `write_partition`. |
| `lvi.rs` | The last-value index: compute the newest row per series, merge it with the previous index, read and write it. |
| `commit.rs` | Writes manifests, the manifest list and new table metadata, then commits with `write_if_absent`. Retries up to 10 times when another writer wins. Three kinds of change: append, replace (compaction) and delete (retention). |
| `ops.rs` | The operations users call: `Table::append` (with inline maintenance) and `Table::maintain` (compaction with dedup, retention, snapshot expiry, file cleanup). |
| `query.rs` | The SQL reader. `Session` wraps a DataFusion context; `TimelakeProvider` plans scans with file pruning; `LatestRewrite` rewrites latest-row queries to read the index; `time_bucket` is registered here. |
| `error.rs` | Error types: not found, already exists, invalid input, conflict, storage, and so on. |

Tests: `crates/timelake/tests/lifecycle.rs` creates tables, appends, queries, maintains and checks results, all on local disk.

## Follow an append through the code

`timelake append iot.readings day1.csv`, or `t.append(batch)` in Python, ends up in `Table::append` (`ops.rs`):

1. `sort_and_split` (`write.rs`): match columns to the table, compute each row's day, sort by day, series key and time, and cut the batch into one piece per day.
2. `write_partition` (`write.rs`): write each day's rows as Parquet under `data/time_day=…/`, up to eight days in parallel. Returns a description of each file (path, size, row count, min/max per column).
3. `latest_per_series` (`lvi.rs`): the newest row of each series in the new data.
4. `commit` → `try_commit` (`commit.rs`): write a manifest for the new files and the merged last-value index at the same time, then the manifest list, then the new metadata. With more than eight manifests, they are merged into one so reads stay quick.
5. `publish` (`commit.rs`): `write_if_absent(vN+1.metadata.json)`. If the file already exists, another writer won: delete this attempt's metadata files, reload, and retry. On success, update `version-hint.text`.
6. Back in `append`: if inline maintenance is on, run size-tiered compaction on the days this append touched, and expire old snapshots in batches.

## Follow a query through the code

`timelake sql "…"` or `lake.sql("…")` calls `Session::sql` (`query.rs`):

1. Parse the SQL and find every table it mentions.
2. `prefetch`: load all those tables in parallel: metadata, manifests and the last-value index.
3. DataFusion plans the query. It asks `LakeCatalog` → `NamespaceSchema` for each table and gets a `TimelakeProvider`.
4. The optimizer runs `LatestRewrite`. If the query asks for the newest row per series (or the newest row for some series), the table scan is replaced with a scan of the last-value index.
5. Otherwise `TimelakeProvider::scan_data` drops files whose min/max values can't match the `WHERE` clause, spreads the remaining files over parallel scan tasks, fetches every file footer once, and hands the files to DataFusion's Parquet reader, which skips row groups and pages.
6. DataFusion runs the rest (filters, joins, aggregates) and returns Arrow batches.

## The CLI and the Python package

- `crates/timelake-cli/src/main.rs`: one file. `clap` defines the commands; CSV and Parquet inputs are read with DataFusion; results print as a table, CSV or JSON. Hidden flags (`--bench-runs`, `--proxy-admin`) exist for the benchmark runner.
- `crates/timelake-py/src/lib.rs`: classes `Lake` and `Table`. Each method runs the engine on a shared Tokio runtime and releases Python's GIL while it waits. Data comes in through the Arrow C stream interface, so pyarrow and polars objects work directly. Tests are in `crates/timelake-py/tests`.

## The WebAssembly reader and the TypeScript client

The WASM module never makes network requests. The TypeScript client fetches bytes and hands them in, which keeps the module small and identical in every JavaScript runtime:

1. The client fetches `version-hint.text` and `vN.metadata.json`; `new Table(json)` (`crates/timelake-wasm/src/meta.rs`) parses it.
2. The client fetches the manifest list and manifests; the module parses them (Avro) into a list of files.
3. `planFiles(query)` drops files whose min/max values can't match.
4. For each file, the client fetches the end of the file (the footer). `ParquetFile.plan` (`query.rs`) returns the byte ranges of the row groups and columns needed. The client fetches just those ranges.
5. `Query.push` decodes, filters and aggregates; `finish` returns JSON rows. The client validates them with Zod if a schema was given.

`packages/timelake-client/scripts/build-wasm.sh` compiles the crate, shrinks it with `wasm-opt`, and embeds it as base64 in `src/wasm/inline.js`, so the package loads without a separate `.wasm` file. The generated files are committed; rebuild them after changing `crates/timelake-wasm`.

## The website

| Path | What |
| --- | --- |
| `dashboard/app/(site)` | Landing page, `/docs` (one folder per page) and `/benchmarks`. |
| `dashboard/app/(app)/explore` | The Explorer: tables, a table's details and latest values, a series chart, a SQL console. |
| `dashboard/app/api` | Two route handlers used by the Explorer: `/api/sql` and `/api/series`. |
| `dashboard/lib/lake` | The Explorer's data layer, with two backends behind one interface: `wasm.ts` reads a public warehouse with `@timelake/client` (used on timelake.dev, no SQL), `cli.ts` runs the `timelake` binary (local, full SQL). `index.ts` picks one by environment variable. |
| `dashboard/lib/benchmarks.ts` | Reads the result files in `dashboard/data/results` (a copy of the ones in `bench/results`, made by `bun run sync-results`) and computes the numbers for the charts. |
| `dashboard/components` | Page pieces (diagrams, charts, tables); `components/ui` holds shadcn/ui components. |

Vercel builds and deploys the site on every push to `main` (project root `dashboard/`). The demo data on timelake.dev is a small warehouse on Vercel Blob, built by `scripts/build-demo-warehouse.sh` and uploaded with `bun run upload-demo`.
